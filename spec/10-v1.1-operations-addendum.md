# v1.1 Operations Addendum

## Scope decision
v1.1.0 does not redesign the participant product. All v1.0.1 participant routes, UI expectations, invitation-code signup, weekly judging, streak/failure rules, owl growth, community and completion behavior remain the compatibility baseline.

The administrator area is expanded only for operational recovery:
- participant progress overview,
- official weekly outcome inspection,
- submission-attempt inspection,
- explicit weekly-result correction with a required reason,
- immutable audit trail of those corrections.

This is not a content-moderation workflow. The administrator does not approve ordinary weekly submissions; ordinary participant submissions continue to use the same automatic-verification/self-report fallback as v1.0.1.

## Data responsibilities
- Supabase Auth: identity, password, session.
- `profiles`: display name and role.
- `challenges`: current derived challenge state for fast reads.
- `weekly_results`: one official outcome per challenge/week and historical state snapshots.
- `submissions`: submitted URL attempts; old attempts are preserved when an administrator replaces the accepted link.
- `invite_codes`: one-code/one-person signup gate.
- `audit_logs`: administrator corrections only.

`analytics_events` and `challenge_events` are removed. User-visible failure/recovery history is represented by the `effect` snapshot on `weekly_results`, and routine product analytics are not stored in the operational PostgreSQL database.

## Recovery rule
`weekly_results` is the historical source used to rebuild current challenge summary fields. Whenever an administrator corrects a weekly outcome, the database recalculates streak, longest streak, consecutive failures, stage penalty, reset count, success count and failure count in chronological order. This prevents manual corrections from leaving dashboard/community values inconsistent with history.
